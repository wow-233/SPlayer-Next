# 多人一起听优化记录（2026-09-29）

## 本次修改

页面沿用原项目 `Collection`、`Liked` 和 `SongList` 的结构：原生封面、紧凑歌曲信息、操作栏及歌曲列表。复用 `STabs`、`SImg`、`SDrawer`、`SPopover` 和 `SVirtualList`，配色和字号跟随应用主题。成员从头像入口查看；推歌侧栏默认显示最近播放，支持连续添加。

已在独立测试配置中检查深色、浅色主题、980px 窗口、推歌侧栏自动聚焦及待播列表。截图使用模拟房间资料；这些界面检查不代表真实房间同步测试。

| 问题                                             | 修改后的行为                                                           |
| ------------------------------------------------ | ---------------------------------------------------------------------- |
| 当前歌曲加载失败后可能一直无声                   | 保留房间时间线，按退避间隔重试当前歌曲；加载完成后对齐最新进度         |
| 本机音源失败可能触发全房间切歌                   | 本机失败只请求恢复播放；主动切歌和自然播完分别处理                     |
| 退出或切换房间后，旧操作仍可能更新页面或播放歌曲 | 异步请求绑定房间会话，旧响应失效；同一房间重新加入也受保护             |
| 恢复播放时从本机旧进度继续                       | 恢复前先查询官方房间进度；系统播放事件也触发重新同步                   |
| 普通播放列表与房间列表不一致，清空后本机停止     | 普通列表显示房间歌曲；房间内隐藏本地删除、清空和拖排序入口             |
| 推歌需要滚动查找搜索框                           | 页头与待播区均可打开原生推歌侧栏；搜索内容保留，便于连续添加           |
| 搜索结果的“立即播放”容易误切整个房间             | 搜索结果集中提供推歌；切歌仍可在待播列表明确操作                       |
| 已在播放的歌曲也显示“已在待播”                   | 区分“正在播放”和“已在待播”                                             |
| 置顶次数没有体现自己是否已置顶                   | 使用官方队列实例编号及 uped 状态，显示次数和“已置顶”，防止重复提交     |
| 成员、歌曲资料、置顶历史拖慢状态刷新             | 附加信息后台补齐；歌曲资料请求合并并限制缓存和失败重试频率             |
| 连续推歌操作互相覆盖                             | 操作按提交顺序处理；按钮分别显示等待状态，退出房间后取消尚未执行的请求 |
| 成功后偶尔重新出现旧错误                         | 页面丢弃较早状态查询的失败结果                                         |

## 暂未接通

- 官方待播删除：9.5.70 APK 的待播界面使用远程 `rn-tt-playlist`，现有资料未能确认删除请求。未提供仅在本机隐藏歌曲的假删除。
- 跨设备即时推送：尚未接入官方消息推送通道。v1.3.5 使用约 2 秒一次的房间状态查询，实际可见延迟还包含网络和歌曲资料请求时间；限流或断网时会退避。
- 验证范围：自动化覆盖模拟网络失败、旧请求返回和队列操作；真实多设备同步精度仍需在有效官方房间中实测。

## 体验时建议检查

1. 创建或加入房间后，在手机和桌面端分别推歌、置顶，核对待播顺序与次数。
2. 桌面端暂停片刻再恢复，确认跟随房间当前歌曲与进度。
3. 自然播完时确认不会产生主动切歌提示；暂时无法播放的歌曲不应清掉他人的待播。
4. 普通播放列表应显示房间歌曲，不出现本地清空、移除入口。

## v1.3.5：他人推歌延迟、歌手名与成功提示

- 房间状态不再只等待 20～30 秒的保活心跳。界面每 2 秒读取官方快照，同时更新队列、成员和播放时间线；同一时间只发一次查询，失败逐步退避至 30 秒。
- 查询带会话、操作版本和请求顺序校验，迟到的心跳不能覆盖新队列；退出后旧查询不能重新恢复房间。
- 新歌曲资料随本次查询补齐，成功后不额外等待原来的 5 秒节流；置顶次数查询间隔由 10 秒降为 4 秒。
- 歌手名丢失来自宿主插件结果的 IPC 清理：`data → queue → track → artists → artist → name` 超过旧的 6 层限制。提高至 16 层，保留不可克隆字段过滤和深度限制；界面额外过滤空歌手名。
- 9.5.70 APK 的 `LTMultiSongOperateResultCode.SUCCESS` 为 0，`failedMsg` 成功时也可以有文案。现在只按非零失败码拒绝操作，推歌/置顶成功显示原生绿色对勾，并执行队列更新。

验证：27 项插件测试、5 项宿主测试、插件沙箱 smoke、主进程和界面类型检查、ESLint、生产构建通过。独立测试配置中，用模拟插件资料经过真正的插件进程和 IPC，确认多歌手姓名完整显示，点击置顶后提示为绿色对勾。未用用户账号执行多设备实房间操作。

内存抽样：旧独立测试配置主界面 159 MB、插件进程 77 MB；新独立测试配置主界面 136 MB、插件进程 103 MB（加载模拟测试插件后的 60 秒样本）。两次运行资料不同，仅用于检查，不能据此宣称内存优化。
